## 1. Repository map

**Purpose.** `reportifyr` generates traceable Microsoft Word reports for pharmacometrics/clinical analysis: analysts save figures/tables through `*_with_metadata()` wrappers that write JSON provenance sidecars (git author, script path, blake3 hash), place `{rpfy}:filename.ext` "magic strings" in a docx shell, and the package inserts formatted artifacts, footnotes, and alt-text into the document, with hash-based skip of unchanged artifacts. It is a hybrid: an **R package** (user-facing API) wrapping an **embedded Python package** `reportipyr` (docx engine, python-docx) invoked as a subprocess via `uv` (environment owned by the external `pyro` R package).

**Entry points.**
- R exported API (NAMESPACE): orchestrator `build_report()` (`R/build_report.R`); step functions `add_tables()` (`R/add_tables.R`), `add_plots()` (`R/add_plots.R`), `add_footnotes()` (`R/add_footnotes.R`), `remove_tables_figures_footnotes()`, `finalize_document()`; analysis-time savers `ggsave_with_metadata()`, `write_csv_with_metadata()`, `save_rds_with_metadata()`, `write_object_metadata()`; provenance `rpfy_context()`, `shiny_source()`, `script_source()` (`R/rpfy_context.R`, `R/source_meta.R`); scaffolding `initialize_report_project()`, `sync_report_project()`; validation `validate_docx()`, `validate_config()`, `validate_object()`; logging `toggle_logger()`, `get_log_file()`.
- Python CLI: `inst/python/reportipyr/cli.py`, run as `uv run -m reportipyr.cli <subcommand>`; 14 subcommands (add-figure, add-figure-alt-text, add-table-alt-text, add-figure-footnotes, add-table-footnotes, remove-footnotes, remove-tables, remove-figures, remove-magic-strings, remove-bookmarks, keep-caption-next, check-alt-text-magic, validate-docx, add-path-overlay, parse-magic-string).
- Load hooks: `R/zzz.R` `.onLoad` finds project root from cwd, prunes `.rpfy-logs/`, and configures a session log file; `.onAttach` prints options status (calls `pyro::get_uv_path`).

**Intended layering** (inferred from `build_report.R`, README, and `R/reportifyr.R` package doc): user API (R) → validation (R: `validate_input_args`/`validate_docx`) → docx engine (Python subprocess) — **except tables, which are inserted in R** via officer/flextable while being *removed* in Python (`tables.py`). Analysis-time metadata production (R) and report-time metadata consumption (Python) communicate via the `<name>_<ext>_metadata.json` sidecar convention and via hashes embedded in docx alt text.

**Most load-bearing files.**
1. `R/utils.R` — `run_python_script()` is on every Python call path (one exception: `R/validate_docx.R`); also project-root and provenance detection.
2. `inst/python/reportipyr/magic.py` + `alt_text.py` — magic-string grammar and hash/skip-unchanged logic consumed by every Python subcommand and (partially reimplemented) by `R/add_tables.R`.
3. `inst/extdata/config.yaml` — its keys are read ad hoc in ≥6 R sites (`yaml::read_yaml`) and ~20 Python sites (`config.get(key, inline-default)`).

**Cross-cutting concerns.**
- *Errors*: R `stop()` + `log4r::error`; Python raises or `raise SystemExit(1)` (`footnotes.py:619,722`, `cli.py:48`); the boundary is process exit status + stderr; `validate-docx` additionally returns structured JSON over stdout (`validate.py` → `R/validate_docx.R`). `build_report.R:146-166` wraps only the footnotes step in `tryCatch`+`suppressWarnings`; other steps unprotected.
- *Config*: no single composition point; each function re-reads YAML; defaults exist in three places (shipped yaml, R code branches, Python `config.get` defaults) — see hypothesis 3.
- *Logging*: R log4r logger + lazy session file in `.rpfy-logs/` (`R/toggle_logger.R`, `R/zzz.R`); Python logs everything to stderr with `[py]` tag (`inst/python/reportipyr/logging.py`), mirrored to the R log file by the callback in `R/utils.R:264-284`, console-filtered by `RPFY_VERBOSE`.
- *Validation*: `validate_input_args` + `validate_docx` at the top of each doc function; `validate_config` only called from `add_footnotes()` and only when the user passes a config (`R/add_footnotes.R:139-141`).
- *Concurrency*: none — synchronous subprocess pipeline with intermediate `-int/-clean/-tabs/-tabsfigs` docx files on disk.
- *Auth/trust*: local tool; path traversal from magic strings guarded by twin `safe_resolve` implementations (`R/utils.R:377-401`, `inst/python/reportipyr/util.py:5-13`).

**Build/test/CI.** Standard R package (roxygen2); R dependency env via `rv` (`rproject.toml`, internal PRISM/pyro repositories); Python deps not declared in-repo — pinned by the external `pyro` package's "reportifyr" group (`pyro::write_group_to_pyproject`). CI: `R-CMD-check.yaml` (mac/win/linux, R 4.3–4.5, rv-based), `python-tests.yaml` (pytest on 3.11 with **unpinned** latest python-docx/pillow/pyyaml), `r-release.yml` (binary release matrix). R tests (~2,100 lines, `tests/testthat/`) cover pure-R utilities with `mockery` stubs at the processx/pyro boundary; Python tests (`inst/python/tests/`) cover docx-manipulation units; no end-to-end R→Python pipeline test anywhere in CI.

## 2. Risk hypotheses (ranked)

### H1 — Split-brain docx engine: tables in R, everything else in Python, with duplicated invariants
- **Hypothesis**: The magic-string grammar and the "artifact already present" (skip-unchanged) invariant are implemented independently in R (`R/add_tables.R`) and Python (`magic.py`, `figures.py`, `tables.py`) and have already drifted: R's table path parses magic strings with a plain regex + `gsub("\\{rpfy\\}:", "", ...)` (`R/add_tables.R:72-74,102`) and cannot handle the multi-entry/`<args>` grammar that `magic.parse_magic_entries` supports; `{rpfy}:[a.csv, b.csv]` or `a.csv<...>` would be resolved as a literal filename.
- **Signal**: `R/add_tables.R:226-255` re-implements in xml2 the "next sibling is a table → skip insertion" check whose removal-side counterpart lives in `tables.py` (`remove_tables`, reconciliation); `R/utils.R:377` vs `inst/python/reportipyr/util.py:5` are twin `safe_resolve`s; `R/add_tables.R:174-179` re-derives the metadata filename convention that Python derives in `footnotes.py:36-40` and `alt_text.py:19-22`.
- **If true, cost**: any grammar or skip-unchanged change must be made in two languages with no shared tests; tables silently behave differently from figures for the same magic-string syntax; the drift is invisible until a report renders wrong.
- **Investigation sketch**: enumerate the magic-string grammar accepted by `magic.py` (incl. tests `inst/python/tests/test_parse_magic_string.py`) and check each construct against `add_tables.R`'s parsing; compare R's already-present check against `tables.py`'s skip/reconcile pathways for the same docx state; grep `rpfy}` across both trees.
- **Confidence**: high.

### H2 — The positional-adjacency convention is enforced nowhere and implemented differently everywhere
- **Hypothesis**: The whole system rests on "artifact paragraph(s) immediately follow their magic-string paragraph, in entry order", but each module encodes it with different index math, so mixed png/non-png entry lists or user-inserted content between magic string and artifact desyncs them differently — corrupting alt-text/hash assignment and producing skip-unchanged false positives.
- **Signal**: `figures.py:527-533` (`remove_figures`) indexes drawings as `paragraphs[i+j+1]` where `j` ranges over *all* entries including non-png; `figures.py:101-104` (`add_figure`) skips non-png entries so inserted drawings don't correspond 1:1 with entries; `alt_text.py:299-335` advances `drawing_offset` only when a drawing is found, while `alt_text.py:596-613` (`extract_artifact_hashes`) breaks out of the loop on the first non-paragraph sibling; `footnotes.py:472-481` finds figure paragraphs by scanning forward for any `pic:pic`.
- **If true, cost**: stale artifacts kept in a "validated" report or hashes attached to the wrong figure — a data-integrity failure in regulated deliverables, the exact thing the hash machinery exists to prevent.
- **Investigation sketch**: construct a docx with `{rpfy}:[a.png, b.csv, c.png]` and one with a user paragraph between magic string and figure; trace add → alt-text → remove (skip_unchanged on) through each module's index arithmetic; check `inst/python/tests/` for any mixed-extension fixture (none apparent).
- **Confidence**: high.

### H3 — Config keys and defaults are triplicated (shipped yaml / R validator / Python `config.get`) and validation is optional
- **Hypothesis**: There is no single source of truth for config keys or defaults, and the copies already disagree; misconfiguration is silently absorbed.
- **Signal**: shipped `inst/extdata/config.yaml` sets `skip_unchanged: TRUE` while every Python consumer defaults it to `False` (`figures.py:482`, `tables.py:170`, `footnotes.py:739`); RTF saving defaults to **on** when no config is passed (`R/write_csv_with_metadata.R:66-73`, `R/save_rds_with_metadata.R`) but the shipped config says `save_table_rtf: FALSE`; `R/validate_config.R` is a 312-line hand-maintained if-chain invoked only from `add_footnotes()` and only when the caller supplies a config (`R/add_footnotes.R:139-141`) — `build_report`/`add_plots`/`add_tables` never validate; unknown/typo'd keys are never reported anywhere.
- **If true, cost**: user sets `skip_unchange: true` (typo) or relies on a default that differs between the "no config" and "default config" paths and gets silently different behavior; every new config key adds a fourth place to forget.
- **Investigation sketch**: grep `config\$` (R) and `config.get(` (Python), build the key×default×validator matrix, and diff it against `inst/extdata/config.yaml` and `R/validate_config.R`; trace one key (`skip_unchanged`) through both "config supplied" and "config NULL" paths of `build_report`.
- **Confidence**: high.

### H4 — Body-level vs cell-level duplication inside the Python modules is already drifting (multi-figure order/labels in cells)
- **Hypothesis**: The ~150-line body-paragraph and table-cell code paths duplicated in `figures.py`, `footnotes.py`, and `alt_text.py` have drifted; concretely, multi-figure insertion into a table cell comes out in reversed order with wrong labels.
- **Signal**: body path reverses the figure list before inserting each at `magic_idx+1` (`figures.py:96-99`, insert at `figures.py:137-138`) and compensates label indices (`figures.py:121-125`); the cell path does **not** reverse (`figures.py:241`) yet inserts every figure via `cell_par._element.addnext(...)` (`figures.py:308`), which places the last-processed figure first, and uses `fig_idx` directly for labels (`figures.py:296-299`). Magic-string re-serialization is also duplicated verbatim at `figures.py:548-568` and `figures.py:651-671`.
- **If true, cost**: cell figures render in reverse order with mislabeled A/B panels; every fix to one path silently misses the other (three modules × two paths).
- **Investigation sketch**: desk-check or run `add_figure` on a cell magic string with 2–3 pngs; then diff each module's body vs cell block for other divergences (alt-text offset handling, footnote combination rules).
- **Confidence**: high (the order inversion is near-mechanical; verify before reporting).

### H5 — Path derivation by string substitution and the intermediate-file sweep can mangle user files
- **Hypothesis**: `make_doc_dirs()` and `build_report()` manipulate paths with unanchored substitutions and bulk-move directory contents, which misbehaves for paths merely *containing* the keywords and for output dirs holding unrelated files.
- **Signal**: `R/make_doc_dirs.R` does `sub("shell", "draft", base_path)` then `sub("draft", "final", base_path)` on the **whole path** (a user dir like `.../michelle/...` or `.../drafts-2026/...` gets rewritten); `gsub(".docx", "-int.docx", docx_out)` with unescaped dot appears in `R/add_plots.R:73`, `R/add_tables.R:59`, `R/finalize_document.R`; `R/build_report.R:179-191` moves *every* file in `dirname(docx_out)` except `docx_in`/`docx_out`/`readme.txt` into `intermediate_files/`, with `file.rename` return values unchecked.
- **If true, cost**: intermediate/output files written to nonexistent paths, or a user's unrelated documents relocated without warning; failures are silent.
- **Investigation sketch**: unit-level desk-check `make_doc_dirs` with adversarial paths (contains "shell"/"draft" as substrings; docx not under a `shell/` dir); enumerate what lives in a real `report/draft/` dir when `build_report` runs twice.
- **Confidence**: high mechanism / medium likelihood-of-user-impact.

### H6 — The metadata sidecar contract is convention-only, spread across ≥7 sites in two languages, and hard-indexed on the consumer side
- **Hypothesis**: The `<name>_<ext>_metadata.json` naming and the JSON schema (`object_meta.footnotes.notes`, etc.) are re-derived at every site with no shared helper or schema check; producer (R) and consumer (Python) can silently disagree, and older/hand-edited files crash the footnote step.
- **Signal**: naming duplicated at `R/write_object_metadata.R:94-99`, `R/add_tables.R:174-179`, `R/validate_object.R:29-32`, `R/update_object_footnotes.R:30`, `R/preview_metadata_files.R:24`, `inst/python/reportipyr/footnotes.py:36-40`, `alt_text.py:19-22`; `footnotes.py:99,107-118,149` hard-indexes `metadata["object_meta"]["footnotes"]["notes"]` (KeyError → uncaught → nonzero exit) while `source_meta` alone got a legacy-fallback handler (`footnotes.py:67-101`).
- **If true, cost**: schema evolution requires synchronized edits in 7 files; a single pre-0.4 metadata file aborts an entire report build with a raw traceback.
- **Investigation sketch**: grep `_metadata.json`; feed `add_table_footnotes` a metadata file missing `footnotes.abbreviations`; compare fields written by `write_object_metadata` against every field Python reads.
- **Confidence**: medium-high.

### H7 — Error-channel inconsistency at the R↔Python boundary
- **Hypothesis**: The de facto error strategy (Python stderr + exit status → `run_python_script` → log/console) has exceptions that lose diagnostics: `validate_docx()` bypasses the shared runner and discards stderr, and `build_report` protects only the footnotes step.
- **Signal**: `R/validate_docx.R:44-70` calls `processx::run(..., error_on_status = FALSE)` with no stderr callback — a Python traceback there yields only "validate-docx returned no output"; `R/build_report.R:146-166` wraps `add_footnotes` in `tryCatch`+`suppressWarnings` while the remove/add-table/add-plot steps have no cleanup on failure, leaving `-clean`/`-tabs` intermediates and a half-swept output dir.
- **If true, cost**: the most common support scenario (broken venv, bad docx) produces the least diagnosable failure; partial builds leave confusing state.
- **Investigation sketch**: check what `pyro::run_python_script` does on nonzero exit (external dep — may need to read pyro or test); simulate a Python exception in `validate-docx` and in `add-figure` and observe user-visible output and leftover files.
- **Confidence**: medium.

### H8 — Test coverage is anti-correlated with risk, and Python CI tests a different dependency set than production
- **Hypothesis**: The riskiest code (orchestration, R↔Python boundary, skip-unchanged round trip) has no automated coverage, while pure utilities are well tested; CI's Python deps are unpinned latest but production runs pyro-pinned versions.
- **Signal**: `tests/testthat/` has no test for `build_report`, `add_plots`, `add_tables`, or `add_footnotes` (processx/pyro stubbed via mockery only in `test-validate_docx.R`, `test-get_git_info.R`); `.github/workflows/python-tests.yaml:27-29` installs unpinned `python-docx pillow pyyaml`; no workflow ever runs R and Python together.
- **If true, cost**: regressions in exactly the hypothesized areas (H1–H5) ship undetected; green CI does not imply the user-installed (pyro-pinned) combination works.
- **Investigation sketch**: confirm the coverage map (grep testthat for the pipeline functions); compare pyro's pinned python-docx version against latest for known API changes; check whether `inst/python/tests/data/*.docx` fixtures exercise cell-level or multi-figure paths.
- **Confidence**: medium-high.

## 3. Questions for the maintainer (each with default)

**Q1 (→H1).** Tables are inserted in R (officer/flextable) while figures/footnotes/alt-text and all *removal* run in Python. Is this split permanent and intentional (flextable formatting is R-only), or is table insertion expected to migrate to Python eventually? **Default:** permanent and intentional — review for drift between the two implementations, not for unification.

**Q2 (→H1/H2).** Is the multi-entry / `<key: value>` magic-string grammar (`{rpfy}:[a.png, b.png]<width: 4>`) supported for **figures only**, with tables restricted to a single plain `{rpfy}:name.csv`? **Default:** figures only by design, but nothing enforces or documents it — R's table path silently mis-parses the rich grammar, which counts as a finding.

**Q3 (→H2).** Is "artifact paragraphs immediately follow the magic-string paragraph, with nothing in between" a documented contract users must uphold in Word, or must the tooling tolerate user-inserted content there? **Default:** it is a soft convention users can and do violate; index-desync under violation is a real failure mode worth reporting.

**Q4 (→H3).** Should `validate_config()` run at every entry point that accepts `config_yaml` (build_report, add_plots, add_tables, validate_docx), or is the current add_footnotes-only, user-config-only invocation intentional? **Default:** accidental inconsistency — report it.

**Q5 (→H5).** `make_doc_dirs()` derives draft/final paths via `sub("shell", "draft", path)` on the whole path. Is the `report/shell|draft|final` layout from `initialize_report_project()` the only supported layout? **Default:** yes it's the intended layout, but `make_doc_dirs`/`build_report` are exported and accept arbitrary paths, so substring corruption is still in scope.

**Q6 (→H5).** `build_report()` moves everything in `dirname(docx_out)` (except in/out docs and readme.txt) into `intermediate_files/`. Is sweeping arbitrary user files an accepted behavior of the draft directory, or intended to catch only reportifyr's own intermediates? **Default:** intended only for its own intermediates; relocating unrelated files is a defect.

**Q7 (→H4).** For multiple figures in one **table-cell** magic string, is rendering order specified anywhere? The body path reverses the list before insertion; the cell path does not, yet inserts each figure directly after the magic paragraph. **Default:** cell order should match body order (document order = list order); the divergence is a bug candidate.

**Q8 (→H7).** Does `pyro::run_python_script()` raise an R error on nonzero Python exit status (making SystemExit(1) in footnotes.py reliably abort R callers)? pyro is out-of-repo so I could not verify. **Default:** yes it errors; review then focuses on the `validate_docx.R` bypass and its stderr loss.

**Q9 (→H6).** Are metadata JSON files written by pre-0.4 reportifyr versions still expected in live projects (the `source_meta` legacy handler suggests yes, but `object_meta` fields are hard-indexed)? **Default:** yes — legacy or hand-edited metadata must degrade gracefully, not crash the build.

**Q10 (→H8).** Is there an out-of-repo integration test (internal pipeline, example project) that exercises the full R→Python build on real docx templates? **Default:** no — the in-repo test gap on the orchestration path is real and reportable.

## REVIEW ADDENDUM (survey pass, 2026-07-06)

### CONTEXT

- Codebase: `reportifyr` — R package + embedded Python package (`inst/python/reportipyr/`) that assembles Microsoft Word reports from `{rpfy}:file.ext` magic strings, inserting figures/tables/footnotes/alt-text with hash-based provenance tracking; Python is invoked via `uv` subprocess (env owned by external `pyro` R package).
- Primary consumers: internal pharmacometrics/clinical analysts at A2-Ai and GSK producing regulated report deliverables; correctness of what lands in the final docx (right artifact, right footnote, no stale content) matters more than performance.
- Known constraints or intentional decisions worth flagging up front: dual-language design is deliberate (python-docx does what officer cannot); Python dependency pinning lives in the external `pyro` package, not this repo; `.rpfy-logs/` session logs and interactive confirmation prompts are product features. Applied defaults for unanswered maintainer questions are noted `[Q#]` below.
- Areas of specific concern: R↔Python duplicated invariants; the positional-adjacency and hash-in-alt-text machinery (`skip_unchanged`); config sprawl; error propagation across the subprocess boundary.

### PRIORITY TARGETS

Allocate ~80% of investigation here. Each is a hypothesis to confirm or refute.

1. **R/Python split-brain on magic strings and skip-unchanged (survey H1).** R inserts tables (`R/add_tables.R`) with its own regex (`add_tables.R:72-74`), its own `gsub`-based filename extraction (`:102`), its own already-present XML check (`:226-255`), and its own metadata-filename derivation (`:174-179`); Python owns the richer grammar (`inst/python/reportipyr/magic.py::parse_magic_entries`) and the removal/reconciliation side (`tables.py`). Verify whether magic strings using list/`<args>` syntax for tables mis-resolve in R, and whether R's skip check and `tables.py`'s reconcile paths agree on the same docx states. Also compare twin `safe_resolve`s (`R/utils.R:377-401` vs `inst/python/reportipyr/util.py:5-13`). [Q1][Q2]
2. **Positional-adjacency index math across modules (survey H2).** For mixed-extension magic strings (`[a.png, b.csv, c.png]`) and for user content inserted between magic string and artifact, trace: `figures.py::add_figure` (skips non-png; `:101-104`), `figures.py::remove_figures` (`paragraphs[i+j+1]` over all entries; `:527-533`), `alt_text.py::add_figure_alt_text` (`drawing_offset`; `:299-335`), `alt_text.py::extract_artifact_hashes` (`:596-613`), `footnotes.py::add_figure_footnotes` (forward pic scan; `:472-481`). The question is whether these can attach hashes/alt text to the wrong artifact or produce skip-unchanged false positives (stale artifact kept). Data-integrity severity if confirmed. [Q3]
3. **Config sprawl and default drift (survey H3).** Build the key×default matrix across `inst/extdata/config.yaml`, `R/validate_config.R`, and every `config.get(` in `inst/python/reportipyr/` plus `config$` in `R/`. Known discrepancies to verify: `skip_unchanged` shipped TRUE vs Python default False (`figures.py:482`, `tables.py:170`, `footnotes.py:739`); RTF export on-by-default without config vs `save_table_rtf: FALSE` in shipped config (`R/write_csv_with_metadata.R:66-73`); `validate_config` called only from `add_footnotes` and only for user-supplied configs (`R/add_footnotes.R:139-141`); unknown keys never diagnosed anywhere. [Q4]
4. **Body vs cell duplication drift in Python (survey H4).** Diff the duplicated body-paragraph vs table-cell blocks in `figures.py` (add: `:46-228` vs `:231-396`; remove: `:466-571` vs `:573-681`), `footnotes.py`, `alt_text.py`. Concrete suspected bug: cell path inserts multiple figures via `addnext` without reversing the list (`figures.py:241,308`) — reversed rendering order and wrong A/B labels (`:296-299`) vs body path (`:96-99,121-138`). Also verbatim-duplicated magic-string re-serialization (`figures.py:548-568` vs `:651-671`). [Q7]

### REPO MAP

**Purpose.** `reportifyr` generates traceable Microsoft Word reports for pharmacometrics/clinical analysis: analysts save figures/tables through `*_with_metadata()` wrappers that write JSON provenance sidecars (git author, script path, blake3 hash), place `{rpfy}:filename.ext` "magic strings" in a docx shell, and the package inserts formatted artifacts, footnotes, and alt-text into the document, with hash-based skip of unchanged artifacts. Hybrid: an **R package** (user-facing API) wrapping an **embedded Python package** `reportipyr` (docx engine, python-docx) invoked as a subprocess via `uv` (environment owned by the external `pyro` R package).

**Entry points.**
- R exported API (NAMESPACE): orchestrator `build_report()` (`R/build_report.R`); step functions `add_tables()`, `add_plots()`, `add_footnotes()`, `remove_tables_figures_footnotes()`, `finalize_document()`; analysis-time savers `ggsave_with_metadata()`, `write_csv_with_metadata()`, `save_rds_with_metadata()`, `write_object_metadata()`; provenance `rpfy_context()`, `shiny_source()`, `script_source()`; scaffolding `initialize_report_project()`, `sync_report_project()`; validation `validate_docx()`, `validate_config()`, `validate_object()`; logging `toggle_logger()`, `get_log_file()`.
- Python CLI: `inst/python/reportipyr/cli.py`, `uv run -m reportipyr.cli <subcommand>`; 14 subcommands (add-figure, add-figure-alt-text, add-table-alt-text, add-figure-footnotes, add-table-footnotes, remove-footnotes, remove-tables, remove-figures, remove-magic-strings, remove-bookmarks, keep-caption-next, check-alt-text-magic, validate-docx, add-path-overlay, parse-magic-string).
- Load hooks: `R/zzz.R` `.onLoad` (project-root detection from cwd, log pruning, session log setup); `.onAttach` (options status message, uv probing).

**Module inventory.** R ≈ 4,861 lines; Python ≈ 3,194 lines.

**Intended layering** (inferred from `build_report.R`, README, `R/reportifyr.R`): user API (R) → validation (R) → docx engine (Python subprocess) — except table insertion, which stays in R. Metadata producer (R, analysis time) ↔ consumer (Python, build time) via JSON sidecar convention and alt-text-embedded hashes.

**Most load-bearing.** (1) `R/utils.R::run_python_script` — every Python call except `R/validate_docx.R`; (2) `inst/python/reportipyr/magic.py` + `alt_text.py` — grammar and hash logic used by every subcommand and partially reimplemented in `R/add_tables.R`; (3) `inst/extdata/config.yaml` keys — read ad hoc at ≥6 R and ~20 Python sites.
