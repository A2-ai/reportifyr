## 1. Architecture summary

`reportifyr` is a hybrid R package + embedded Python package (`inst/python/reportipyr/`)
that assembles regulated Word reports: analysts write `{rpfy}:file.ext` magic strings
into a docx shell; the pipeline removes previously inserted artifacts, re-inserts
figures (Python/python-docx), tables (R/officer+flextable), footnotes and alt-text
(Python), with blake3 provenance hashes carried in JSON sidecars and embedded in docx
alt text to enable `skip_unchanged`. Python runs as a `uv` subprocess (env owned by
external `pyro`); the boundary is exit status + stderr (mirrored into a session log by
`R/utils.R::run_python_script`), except `validate-docx`, which returns JSON on stdout.

**Addendum spot-check:** the repo map holds. All listed entry points exist; line
counts, cited line ranges, and the fan-in claims (`run_python_script`, `magic.py`/
`alt_text.py`, `config.yaml`) check out. Two trivia: the CLI has 15 subcommands, not
14 (`inst/python/reportipyr/cli.py:56-167`), and `tables.py` skip logic starts at
`:169`, not `:170`. Nothing marked `(?)` failed verification; pyro-side pinning
remains unverifiable in-repo, as stated.

**Flows traced.**
1. *Happy path* — `build_report()` (`R/build_report.R`): validate → remove-footnotes →
   remove-tables → remove-figures (all Python, each gated by hash checks when
   `skip_unchanged`) → `add_tables()` (R/officer) → `add_plots()` → alt-text →
   footnotes → sweep everything else in the output dir into `intermediate_files/`.
2. *Error path* — Python `SystemExit(1)`/uncaught exception → nonzero exit →
   `pyro::run_python_script` error → R `stop()`. Only the footnotes step is wrapped
   in `tryCatch` (`R/build_report.R:145-166`); `validate_docx` bypasses the shared
   runner entirely and discards stderr (`R/validate_docx.R:64-74`).
3. *Load path* — `.onLoad` finds a project root from cwd, prunes `.rpfy-logs`,
   configures a lazy DEBUG file appender (`R/zzz.R:1-12`, `R/toggle_logger.R`).

**Structural read.** The Python side has a clean core (one grammar module, one cell
iterator, structured validate output). The systemic weakness is that the document
model is *positional adjacency* — "the artifact for entry N of a magic string lives N
paragraphs below it" — and at least six functions implement that convention
independently, three of them incompatibly. The second weakness is that table
insertion lives in R while table removal/reconciliation lives in Python, so the
magic-string grammar and the "already present" predicate each have two
implementations that have already drifted. Config keys are read ad hoc at ~26 sites
with defaults in three places and a validator that is only invoked on one path.

**Survey hypotheses.** H1, H2, H4, H6, H7 confirmed with concrete failure traces
(below). H3 confirmed except one sub-claim **refuted**: the `skip_unchanged`
TRUE-in-shipped-yaml vs False-in-Python-default drift is benign in practice — every
R call site resolves and passes a config file (`R/build_report.R:53-56` et al.), so
the Python defaults only bind for direct CLI use. Also largely refuted: the twin
`safe_resolve`s (`R/utils.R:377-401` vs `inst/python/reportipyr/util.py:5-13`) are
semantically equivalent for realistic inputs (differences: R errors when
`artifact_dir` is missing; Python `realpath` follows symlinks on the leaf, R's
`fs::path_norm` does not — no exploitable or workflow-relevant gap found). H5
confirmed but with smaller blast radius than feared (details in finding 6).

## 2. Primary findings (ranked)

### F1 — Positional-adjacency conventions disagree across modules; mixed-extension magic lists corrupt dimensions, hashes, and footnotes
**Severity: Critical · Category: A/D (structural, data integrity) · Confidence: High**

**Evidence.**
- Insertion inserts *only* `.png` entries as drawings: `inst/python/reportipyr/figures.py:101-104` (body), `:274-277` (cell).
- `remove_figures` indexes drawings by `paragraphs[i + j + 1]` over **all** entries
  including non-png: `figures.py:493-515` (skip check), `:527-533` (removal + dim
  harvesting), same in the cell path `:592-649`.
- `add_figure_alt_text` advances its `drawing_offset` only when a drawing is found
  (`alt_text.py:301-335`), but `extract_artifact_hashes` — the function feeding
  `skip_unchanged` for footnotes — advances unconditionally per entry
  (`alt_text.py:596-613`) and its cell path uses plain `enumerate(entries)`
  (`alt_text.py:657-671`). Two functions in the *same module* disagree on the same
  convention.
- `add_figure_footnotes` only inserts the combined footnote while processing the
  *last* entry (`footnotes.py:468`), which is unreachable when the last entry is
  non-png/missing (`:409-421` `continue`s), and its forward scan collects
  `len(figure_args)` pic-paragraphs — counting non-png entries — so it walks past
  this section's figures into the next one (`footnotes.py:472-481`).

**The issue.** Multi-file magic strings are a documented feature (NEWS.md:363), and
`validate-docx` accepts mixed png/csv lists (`inst/python/reportipyr/validate.py:54-79`).
For `{rpfy}:[a.png, b.csv, c.png]` the document contains drawings at offsets +1 and
+2, but removal/extraction assume offsets +1, +2, +3 map to a, b, c. Concrete traces:

1. *Dimension corruption* (verified step-by-step): after a user resizes figures in
   Word, `remove_figures` harvests the +2 drawing's (c.png's) width/height into
   **b.csv's** args and rewrites the magic string as
   `{rpfy}:[a.png<w,h>, b.csv<c's w,h>, c.png]` (`figures.py:527-568`). On the next
   build c.png is re-inserted at artifact size — the user's sizing is silently lost
   and the junk `<...>` on the csv persists in the document forever.
2. *Hash misattribution*: `extract_artifact_hashes` records c.png's embedded hash
   under the key `b.csv` and finds none for `c.png` (`alt_text.py:596-613`), so
   `_build_unchanged_set` (`footnotes.py:730-752`) and the removal skip checks can
   never classify mixed lists as unchanged — `skip_unchanged` silently degrades to
   always-rebuild for them.
3. *Footnote omitted or misplaced*: `[a.png, b.csv]` → no figure footnote at all
   (last entry short-circuits before the insertion block, `footnotes.py:409-492`);
   `[a.csv, b.png]` → the scan wants 2 pic paragraphs, finds only 1 in this section,
   keeps scanning and anchors the footnote **after the next section's figure**
   (`footnotes.py:472-490`).
4. *User edits between magic string and artifact*: `add_figure`'s "already present"
   check counts only *consecutive* empty drawing paragraphs (`figures.py:54-86`), and
   `remove_figures` only looks at exactly `i+j+1`. A user paragraph inserted between
   magic string and figure means the old drawing is neither detected nor removed, and
   a fresh copy is inserted above it — one duplicate stale figure per build,
   accumulating.

**Blast radius.** Wrong or missing footnotes and stale/duplicate figures in QC-ed
regulated deliverables; corruption is written back into the source document (the
rewritten magic string), so it survives even after the code is fixed.

**Remediation sketch.** Define adjacency in exactly one place: a function that, given
a magic paragraph, returns the ordered list of *matched* (entry → drawing/tbl
element) pairs by scanning actual drawings (and matching alt-text filenames where
present), skipping non-insertable entries. `add_figure`, `remove_figures`,
`add_figure_alt_text`, `extract_artifact_hashes`, `add_figure_footnotes`, and
`check_alt_text_magic_string` all consume it. Alternatively (stronger): stop relying
on position entirely — you already write the magic string into each drawing's
`docPr descr`; match drawings to entries by that. Effort: 2–4 days incl. tests.

### F2 — Cell-path figure insertion reverses document order; alt-text hashes then attach to the wrong images, and the error self-conceals
**Severity: High · Category: A/D · Confidence: High**

**Evidence.** Body path reverses the list and re-inserts at `target_index + 1` so
final order matches the magic string (`figures.py:96-99, 134-138`), with labels
computed as `len(figures) - fig_idx - 1` (`:121-127`). The cell path iterates in
forward order (`figures.py:241`) and uses `cell_par._element.addnext(...)`
(`:308`), so each later figure is inserted directly after the magic paragraph,
pushing earlier ones down: `[A.png, B.png]` renders **B then A**. Labels use the
forward `fig_idx` (`:296-299`), so the stamped letters ride along with their own
images — the displayed sequence reads "B, A".

**The issue.** `add_figure_alt_text`'s cell path then assigns alt text (including the
provenance `[hash:...]`) by entry order to paragraphs in document order
(`alt_text.py:350-390`): A's paragraph-text-plus-hash lands on B's image and vice
versa. Because the misattribution is symmetric, the `is_artifact_unchanged` checks in
`remove_figures`' cell path (`figures.py:592-616`) *pass* — fig A's metadata hash is
compared against A's embedded hash sitting on B's drawing — so the reversed order and
swapped provenance are stable across rebuilds and invisible to `check-alt-text-magic`
only because that check inspects a single following paragraph (`alt_text.py:526-527`).

**Blast radius.** Any multi-figure magic string inside a table cell (the layout
mechanism the package itself suggests for side-by-side figures) produces reversed
figure order, "A"/"B" reading order that contradicts the combined footnote
(`footnotes.py:442-445` labels by entry order), and alt-text/hash provenance attached
to the wrong image — a direct traceability defect.

**Remediation sketch.** Make the cell path mirror the body path: iterate
`reversed(figure_args.keys())` with the same label index arithmetic, or insert with
`addnext` on the *previously inserted* paragraph instead of the magic paragraph.
Add one round-trip test asserting document order == magic-string order in cells.
Effort: hours. (This also shrinks F1's surface; the two blocks should afterwards be
extracted into one shared implementation — see F9.)

### F3 — Table pipeline split-brain: R silently drops list/arg magic strings that Python validation approves, and its "already present" check can skip real insertions
**Severity: High · Category: A/D · Confidence: High**

**Evidence.**
- Grammar: Python owns the full grammar (`inst/python/reportipyr/magic.py:15-77`),
  and `validate-docx` accepts `[t1.csv, t2.csv]` or `tab.csv<...>` as valid entries
  (`validate.py:54-66`). R's `add_tables` extracts the name with a bare
  `gsub("\\{rpfy\\}:", "", text)` (`R/add_tables.R:102`); for list or `<args>` forms,
  `tools::file_ext` then returns `""` (brackets/`<` are not alnum), and the entry is
  dropped at DEBUG level as "non-table file" (`R/add_tables.R:121-123`). Python's
  `remove_tables` and `add_table_footnotes` do the same raw `replace("{rpfy}:", "")`
  (`tables.py:173-175`, `footnotes.py:667`), so `<args>` on a table also breaks
  metadata lookup there (`safe_resolve`/sidecar name built from the raw string).
- Skip check: `process_table_file` scans *all* body paragraphs for the **first** one
  whose text merely *contains* `table_name` as a substring and skips insertion if any
  `w:tbl` follows it (`R/add_tables.R:233-255`).
- `officer::cursor_reach` is called with the unescaped `table_name` interpolated into
  a regex (`R/add_tables.R:220-223`).

**The issue.** Three concrete failure modes: (1) a validated document that uses list
syntax for tables builds "successfully" with the tables silently absent — the only
trace is a DEBUG log line, and `validate_docx` (which runs first, every time) said
everything was fine; (2) substring matching in the skip check: with `mydata.csv`
(unchanged, kept table) earlier in the document and `data.csv` (changed, removed),
processing `data.csv` first matches the `{rpfy}:mydata.csv` paragraph — `"data.csv"`
is a substring — sees the kept table after it, and **skips inserting `data.csv`
entirely**: a silently missing table in the output; (3) regex metacharacters in
table filenames (`(`, `+`, …) break `cursor_reach` and abort the whole build.

**Blast radius.** Missing tables in delivered reports, with the failure mode being
absence rather than error. The grammar asymmetry also means every future grammar
extension must be re-implemented (or explicitly rejected) in four places.

**Remediation sketch.** (a) Make `validate-docx` enforce what the pipeline supports:
reject/warn on list or arg syntax attached to csv/rds entries (one code path,
`validate.py`). (b) In `add_tables`, parse via the Python grammar — a
`parse-magic-string` CLI already exists (`cli.py:165-167`) — or at minimum strip
`<...>` and reject `[...]` loudly. (c) Replace the substring skip check with an exact
match on the magic paragraph (`^\{rpfy\}:` + `fixed` comparison of the parsed name)
and escape `table_name` before `cursor_reach`. Effort: ~1 day.

### F4 — Footnote bookmark `w:id`s are paragraph indexes; `remove_footnotes` resolves the end marker by global id lookup — collisions crash the build
**Severity: High · Category: B/D · Confidence: Medium-High**

**Evidence.** `create_footnote_paragraph` sets both `bookmarkStart` and `bookmarkEnd`
`w:id` to the caller-supplied integer (`footnotes.py:300-302, 341-343`); callers pass
the magic paragraph's index `i` (`footnotes.py:488` figures, `:712` tables) or
`len(paragraphs)+n` for cell footnotes (`:565, 609-612`). `remove_footnotes` finds
the end marker with `doc.element.xpath('//w:bookmarkEnd[@w:id="..."]')[0]` and walks
`getnext()` siblings until identity-match (`footnotes.py:839-849`).

**The issue.** Nothing guarantees these ids are unique: (a) figure and table
footnotes are assigned in two separate CLI passes, each numbering from its own
paragraph indexes — a figure magic at index k and a table magic at index k yield two
`fp_` bookmarks with id k; (b) Word's own bookmarks (`_GoBack`, TOC/cross-reference
bookmarks — routine in regulated report shells) use small integer ids in the same
space. When the id-lookup `[0]` resolves to a *different* element than the paired
end (e.g., the true pair was skipped as unchanged, or a foreign bookmarkEnd with the
same id appears earlier), the sibling walk never identity-matches, `getnext()`
returns `None`, and the next iteration raises `AttributeError` — the remove step
crashes with a traceback, and `build_report` aborts (only footnotes are tryCatch-
wrapped, and this is the *remove* step before that). In the narrower case where a
same-id foreign `bookmarkEnd` sits later in the same paragraph, content between them
is deleted instead. `remove_bookmarks` shares the root cause: it deletes every
`bookmarkEnd` whose id matches a removed `fp_` start (`docx_utils.py:70-87`),
which can strip the end marker of an unrelated user bookmark with a colliding id.

**Blast radius.** Hard failure (or content deletion) of `build_report`/
`finalize_document` on documents containing Word-native bookmarks or both figure and
table footnotes at coinciding indexes — i.e., realistic production shells. The
failure appears only at *rebuild* time, after the document has accumulated edits.

**Remediation sketch.** Resolve the end marker by name-pairing, not id: you already
have a unique `fp_<md5>` name on the start — find the end by scanning forward from
the start within its paragraph (the writer always emits start/end as siblings in one
`w:p`, `footnotes.py:297-343`), and guard the walk against `None`. When writing, pick
ids from `max(existing ids)+1`. Effort: half a day.

### F5 — Config contract enforced (almost) nowhere: validator on one path only, defaults in three places, and a missing key crashes the saver
**Severity: High · Category: E/A · Confidence: High**

**Evidence.**
- `validate_config()` (`R/validate_config.R`) is called from exactly one place:
  `add_footnotes`, and only when the user supplied a config (`R/add_footnotes.R:139-141`).
  `build_report`, `add_tables`, `add_plots`, `finalize_document`, all `remove-*`
  paths, and every Python `config.get(...)` consume the file unvalidated.
- Unknown/misspelled keys are never diagnosed anywhere: the validator is an if-chain
  over known keys (`R/validate_config.R:19-305`), and Python uses `config.get` with
  inline defaults (~20 sites, e.g. `figures.py:482`, `footnotes.py:739`,
  `tables.py:169`).
- Defaults live in three places that can disagree: shipped
  `inst/extdata/config.yaml`, Python `config.get(key, default)` literals, and R
  fallbacks. Verified inversion: RTF export defaults **on** when no config is passed
  to `write_csv_with_metadata` but the shipped config says `save_table_rtf: FALSE`
  (`R/write_csv_with_metadata.R:63-73` vs `inst/extdata/config.yaml:26`).
- Concrete crash: `if (config$save_table_rtf)` with a user config lacking that key is
  `if (NULL)` → "argument is of length zero" (`R/write_csv_with_metadata.R:67`). A
  pre-`add_path_overlay`-era project config (the key was added later; cf.
  `initialize_report_project` only writes the config once, `R/initialize_report_project.R:273-295`)
  reproduces this for any analyst passing their project config to the saver.

**The issue.** A misspelled `skip_unchagned:` or `label_multi_figure:` in a project
config silently reverts behavior to defaults with zero diagnostics, on the exact
pipeline (`build_report`) users run. Meanwhile adding any new key requires touching
the shipped yaml + the validator if-chain + every consuming site's default — three
unlinked places (change amplification; `add_path_overlay` already exists in yaml and
validator but old project configs never receive it).

**Remediation sketch.** One schema (key → type → default), one composition point:
R side, a `load_rpfy_config()` that reads yaml, warns on unknown keys, validates
types, fills defaults, and is called by every entry function; Python side, generate
or mirror the same table in `config.py` and route all `config.get` through it. The
existing `validate_config` collapses to a loop over the schema. Effort: 1–2 days.

### F6 — `build_report`'s output-dir sweep relocates files it doesn't own, with unchecked renames; `make_doc_dirs` derives paths by string surgery with a dead guard
**Severity: Medium · Category: B/E · Confidence: High**

**Evidence.** `R/build_report.R:168-191` moves *every* item in `dirname(docx_out)`
except `docx_out`, `docx_in`, `intermediate_files`, and `readme.txt` into
`intermediate_files/`, comparing raw path strings (no normalization) and ignoring
`file.rename` return values. `R/make_doc_dirs.R:38-58`: `sub("shell", "draft",
base_path)` substitutes the *first* occurrence anywhere in the absolute path;
`gsub(".*/(.*)\\.docx", "\\1", ...)`; and the guard `if (base_path == docx_in)
base_path <- ""` at `:43` can never fire because `base_path` always carries a
trailing `/` from `:38` — for a bare filename input, outputs are directed into a
nonexistent directory named `report.docx/`.

**The issue.** (1) Any other document the team keeps in `report/draft/` — previous
drafts of *other* reports built into the same scaffold dir, review copies — is
silently relocated into `intermediate_files/` on every build. (2) Path-string
comparison means a `docx_out` given as `./report/draft/x.docx` or via a symlinked
prefix does not match `list.files(full.names=TRUE)` output, and the just-written
output itself gets swept. (3) A project path containing `shell` upstream (e.g.
`/data/shellfish-study/...`) redirects the whole derived-path family. (4)
`file.rename` across filesystems fails with only a warning; the sweep then half
happens.

**Blast radius.** Misplaced deliverables and confused review workflows rather than
data loss (files are moved, not deleted), but it fires on every build in shared
draft directories and erodes trust in the output tree.

**Remediation sketch.** Sweep only files the pipeline created: `make_doc_dirs`
already enumerates them (`doc_clean`, `doc_tables`, `doc_tabs_figs`, plus the
`-int`/`-intfigs`/`-inttabs` temp names) — move exactly that allowlist, normalize
paths before comparing, and check rename results. In `make_doc_dirs`, operate on
path components (`dirname`/`basename`, replace only a component equal to `shell`)
and fix/remove the dead guard. Effort: half a day.

### F7 — Metadata sidecar contract is convention at ≥7 sites with hard-indexed consumers; older/hand-made sidecars crash footnotes and table formatting
**Severity: Medium · Category: D/A · Confidence: High**

**Evidence.** Producer naming `<name>_<ext>_metadata.json` re-derived independently:
`R/write_object_metadata.R:94-99`, `R/update_object_footnotes.R:26-31`,
`R/add_tables.R:174-179`, `R/preview_metadata_files.R:47-48` (inverse parse),
`save_rtf` (`R/save_as_rtf.R:11-16`, `.RTF` variant),
`inst/python/reportipyr/alt_text.py:19-22`, `footnotes.py:37-40`. Consumers
hard-index the payload: `metadata["object_meta"]["meta_type"]`,
`...["footnotes"]["notes"]`, `...["abbreviations"]` (`footnotes.py:107-149`) —
`KeyError` → raw traceback → build abort if any key is absent; R side,
`format_flextable(data_in, metadata$object_meta$table1)` passes `NULL` for sidecars
predating the `table1` field, failing the assert in `R/format_flextable.R:25-28` and
aborting `add_tables`. There is no schema-version field in the sidecar
(`R/write_object_metadata.R:68-88`) — only the `source_meta` legacy fallback exists
(`footnotes.py:93-101`, intentional per addendum).

**The issue.** The package's own history already produced sidecars that today's
consumers reject (pre-`table1`, pre-`footnotes`-restructure). Artifacts are
long-lived (OUTPUTS dirs outlive package upgrades in analysis projects), so this is
a recurring class of build breakage, and every new field repeats it.

**Remediation sketch.** Single accessor per side: Python `load_metadata` returns a
normalized dataclass/dict with defaults for absent fields (it already exists at
`footnotes.py:35-47` — push the `.get(..., default)` normalization into it and make
`alt_text.load_artifact_hash` use it); R gains `metadata_path_for(file)` used by all
five R sites, and `write_object_metadata` stamps a `schema_version`. Effort: ~1 day.

### F8 — Error-channel inconsistency at the subprocess boundary: `validate_docx` discards stderr; failures mid-pipeline strand intermediates
**Severity: Medium · Category: B/E · Confidence: High**

**Evidence.** `R/validate_docx.R:64-74` calls `processx::run` directly with
`error_on_status = FALSE`, never touches `result$stderr`, and on empty stdout stops
with "check log file for Python errors" — but the Python stderr was neither shown
nor written to the log (the log-mirroring lives only in `run_python_script`'s
callback, `R/utils.R:264-284`). Every other Python call goes through the callback
runner. Meanwhile in `build_report` only the footnotes step is error-wrapped
(`R/build_report.R:145-166`); a failure in add-figure leaves `-int`/`-intfigs`
intermediates in the draft dir (`R/add_plots.R:113-133` unlinks only on success),
and in `add_footnotes` the second (table) pass reads the output of the first
(`R/add_footnotes.R:103-118`), so a figure-pass failure that pyro surfaces as an
R error aborts, while any regression in pyro's error propagation would silently
chain a stale/missing file into the table pass.

**The issue.** The one entry point that runs before *every* pipeline function
(`validate_docx` is called by `build_report`, `add_tables`, `add_plots`,
`add_footnotes`, `finalize_document`) is exactly the one whose Python-side failure
diagnostics vanish (import errors, broken venv, bad PYTHONPATH → empty stdout, lost
stderr). This is the first thing that fails for users with environment problems, and
it fails with the least information.

**Remediation sketch.** Route validate-docx through `run_python_script` (it already
supports capturing stdout via pyro's return) or at minimum log `result$stderr` via
the same `[py]` callback before stopping. Wrap each `build_report` stage to clean up
(or name-and-report) intermediates on failure. Effort: hours.

### F9 — "Already present / unchanged" invariant has three unrelated implementations (R XML adjacency, Python hash-in-alt-text, Python drawing-count), plus verbatim-duplicated body/cell blocks
**Severity: Medium · Category: A · Confidence: High**

**Evidence.** The skip decision is made by: (1) R: paragraph-substring + next-sibling
`w:tbl` check (`R/add_tables.R:226-255`); (2) Python removal: embedded
`[hash:]`/`[content_hash:]` comparisons (`figures.py:489-522`, `tables.py:180-242`,
`footnotes.py:730-752`); (3) Python insertion: count of consecutive empty drawing
paragraphs vs png count with no hash verification at all (`figures.py:54-86`,
`:243-272`). None share code or definition; each has an independent false-positive
mode (F1.4, F3.2, and: any user-placed image directly under a magic string convinces
`add_figure` the artifact is "already present" and suppresses insertion of the real
one, `figures.py:61-86`). Separately, the body vs cell duplication the survey
flagged is confirmed beyond F2: the magic-string re-serializer is copy-pasted
verbatim (`figures.py:548-568` vs `:651-671`), as are the ~90-line image-sizing
blocks (`figures.py:141-224` vs `:311-394`) — six near-copies that must be edited in
lockstep with nothing enforcing it (F2 is exactly such a drift).

**The issue.** "Should this artifact be (re)built?" is the package's core invariant
— the whole `skip_unchanged` feature — and it currently has no single definition.
Every fix in this review's F1–F3 must be applied to several of these sites; history
shows the copies drift.

**Remediation sketch.** One Python predicate `artifact_state(magic_par, entry) ->
{absent, present_unchanged, present_changed}` built on the hash machinery, used by
insertion *and* removal, body *and* cell (fold the sizing/serialization copies into
helpers at the same time). For R tables, either call into it via a small CLI
subcommand or key the R check on the table's `w:tblDescription` hash instead of
substring adjacency. Effort: 2–3 days, best done together with F1/F2.

### F10 — Test coverage anti-correlated with the risk concentrated above
**Severity: Medium · Category: E · Confidence: High**

**Evidence.** Python tests cover pure helpers and single-figure body-path flows
(`inst/python/tests/`: heavy `test_footnotes.py` on formatting runs, `test_add_figure.py`
only CLI/embedded dimensions — no cell-path, no mixed-extension, no
multi-figure-order, no `remove_footnotes` bookmark test, no `alt_text` adjacency or
`extract_artifact_hashes` test, no `tables.py` reconcile test). R tests
(`tests/testthat/`) cover utilities and validators with mocks at the processx/pyro
boundary; there is no test exercising `add_tables`' skip check, `build_report`'s
sweep, or any R→Python round trip, and CI (`.github/workflows/python-tests.yaml`)
installs unpinned python-docx/pillow/pyyaml while production pins live in pyro —
CI can green on versions users never run. Every bug in F1–F4 sits in untested code;
everything tested is the code least likely to break.

**Remediation sketch.** A small docx round-trip suite in pytest (build → edit →
rebuild) around: mixed lists, cell multi-figures, unchanged-skip, footnote
remove/re-add with a `_GoBack` bookmark present. One R integration test gated on a
local venv. Pin CI Python deps to pyro's versions (export or vendored constraints
file). Effort: 1–2 days initial.

  occurrences; a path with `.docx` elsewhere (dir names, `x.docx.docx`) derails the

## 4. Questions for maintainers

1. Is list/`<args>` syntax *intended* to be figures-only? Nothing states it, and
   `validate-docx` approves list-form tables that `add_tables` then silently drops
   (F3). If intended, the validator should enforce it.
2. Are magic strings for **tables inside table cells** expected to work?
   `officer::docx_summary` surfaces cell text, so `add_tables` will find a cell
   `{rpfy}:tab.csv` and call `cursor_reach`, whose behavior there is untested;
   Python's `remove_tables` only handles body-level tables.
3. What does `pyro::run_python_script` do on nonzero exit — raise, or return a
   status? The entire pipeline's failure story (F8, chained `add_footnotes` passes)
   rests on it raising, and that contract is not verifiable in-repo.
4. Does Word renumber `w:id` on bookmarks when users save? If so, F4's collision is
   more likely (Word compacts ids), and name-based pairing becomes mandatory.
5. `build_report` sweeps `dirname(docx_out)` — is "one report per draft directory"
   an assumed convention? If yes, document it; if no, F6's allowlist fix.
6. `keep_caption_next` runs in both `add_tables` and `add_plots` on successive
   intermediates — intentional idempotence or accidental double work?

## 5. What's good (preserve these)

1. **The provenance design itself.** Blake3 sidecars + hashes embedded in alt
   text/tblDescription + `content_hash`/`grid` with cell-level reconciliation that
   preserves user formatting (`tables.py:107-157`, `alt_text.py:159-268`) is a
   genuinely strong mechanism — the problems above are in the *plumbing around* it,
   not the idea. `_make_bookmark_name`'s documented md5 scheme (`footnotes.py:16-26`)
   is the right pattern: writers and matchers share one function.
2. **The subprocess boundary discipline.** One CLI (`cli.py`) with small composable
   arg helpers, `_parse_bool` correctly handling R's `"TRUE"/"FALSE"`, JSON-on-stdout
   for the one command that returns data, and the `[py]`-tagged stderr→session-log
   callback (`R/utils.R:251-295`) giving a single merged audit log across languages.
   Extend it to `validate_docx` (F8) rather than weakening it.
3. **Shared structural helpers where they exist.** `magic.py` as the single grammar,
   `iter_cell_paragraphs` with its GC-safe dedup (`docx_utils.py:10-27`), and the
   registry-based source handlers (`footnotes.py:75-101`) are the correct shape —
   F1/F9's fix is to pull the adjacency logic up into exactly this kind of module.
